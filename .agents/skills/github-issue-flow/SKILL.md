# Работа с GitHub Issue

Исполнитель ведет задачу целиком: проверяет контекст, реализует изменения, проверяет результат и оформляет PR. Обязательного отдельного исполнителя реализации нет.

## 1. Проверить запрос и репозиторий

Прочитать `AGENTS.md`. Сверить полный идентификатор `SuperLuchito/zero2python`, `origin` и фактическую основную ветку. Не изменять другой репозиторий при несовпадении.

```bash
gh auth status
gh repo view SuperLuchito/zero2python --json nameWithOwner,defaultBranchRef,url,isEmpty
git remote get-url origin
git status --short --branch
```

Использовать GitHub-коннектор вместо CLI, если он покрывает операцию. Сетевой сбой в ограниченной среде не доказывает невалидность учетных данных.

- Одна назначенная Issue — одна ветка и один связанный PR.
- Прямое поручение выполнить готовую Issue разрешает обычные действия до PR включительно. Запрет пользователя на публикацию имеет приоритет: выполнить доступную локальную работу без push и PR.
- Первоначальную настройку и явно локальные поручения можно выполнять без Issue. Не создавать удаленные задачи лишь ради формального прохождения процесса.
- Пустой remote не имеет базового коммита для PR. Подготовить материалы локально; первичную публикацию выполнить по соответствующему поручению, затем проверить основную ветку.

## 2. Проверить Issue и приемку

Загрузить актуальное состояние из GitHub:

```bash
REPOSITORY="SuperLuchito/zero2python"
ISSUE_NUMBER="<номер>"
gh issue view "$ISSUE_NUMBER" --repo "$REPOSITORY" \
  --json number,title,state,url,assignees,labels,milestone,body
```

- Issue должна быть открыта. Проверить связанные PR и блокирующие зависимости через доступное API и ссылки в теле; не считать зависимость закрытой без проверки.
- Не забирать работу другого исполнителя без соответствующего поручения. Неназначенную Issue, которую пользователь поручил выполнить, можно назначить текущему пользователю.
- Прочитать относящиеся к задаче документы и локальные инструкции. Зафиксировать ожидаемый результат, границы, критерии приемки и проверки.
- Метки брать из `.github/labels.yml`: один `type:*`, один `priority:*`, один текущий `status:*` и применимые `module:*`. Проверить их существование на GitHub. Отсутствие косметических метаданных не блокирует понятную задачу: исправить их в пределах полномочий или указать ограничение.
- При `in-progress` найти существующие ветку и рабочее дерево; при `needs-review` — PR. Не создавать дубликаты. При блокирующем статусе проверить причину и не начинать зависимую часть, пока она сохраняется.
- Открытый вопрос блокирует только зависимую часть. Продолжать независимую работу; необходимый вопрос задать с объяснением его влияния и записать в `docs/questions.md`.

## 3. Подготовить рабочее дерево

Краткое название отражает суть задачи и состоит из строчных латинских букв, цифр и дефисов. Проверить итоговое имя ветки.

```bash
SHORT_NAME="<краткое-название>"
DEFAULT_BRANCH="$(gh repo view "$REPOSITORY" --json defaultBranchRef --jq .defaultBranchRef.name)"
REPOSITORY_ROOT="$(git rev-parse --show-toplevel)"
BRANCH="issue/${ISSUE_NUMBER}-${SHORT_NAME}"
WORKTREE_ROOT="$(dirname "$REPOSITORY_ROOT")/worktrees/zero2python"
WORKTREE_PATH="${WORKTREE_ROOT}/${ISSUE_NUMBER}-${SHORT_NAME}"

git check-ref-format --branch "$BRANCH"
git fetch origin
git worktree list --porcelain
git branch --list "$BRANCH"
git branch --remotes --list "origin/$BRANCH"
```

До создания проверить непустую основную ветку и наличие `origin/$DEFAULT_BRANCH`. Если ветка или рабочее дерево существуют, проверить связь с Issue, историю, diff и удаленное состояние; возобновить подходящую работу. Не сбрасывать и не пересоздавать ее автоматически.

Для новой задачи:

```bash
mkdir -p "$WORKTREE_ROOT"
git worktree add -b "$BRANCH" "$WORKTREE_PATH" "origin/$DEFAULT_BRANCH"
```

Дальнейшие изменения и Git-команды выполнять внутри проверенного рабочего дерева. Если среда уже выделила дерево этой задачи, использовать его после проверки ветки и базы. Не делать stash и не очищать исходный checkout.

После подготовки перевести Issue из `status: ready` в `status: in-progress`, если удаленные метки настроены и изменение разрешено. При переходах заменять прежний `status:*`, не накапливать статусы.

## 4. Реализовать и проверить

- Реализовать задачу с применимыми проектными навыками; сверить результат с приемкой и границами Issue.
- Проверить состав файлов, полный diff и `git diff --check`. Новые неотслеживаемые файлы читать отдельно: обычный diff их не показывает.
- Выполнить применимые проверки из Issue, `AGENTS.md` и реального проекта. Для значимого поведения проверить сценарий и существенные ошибки; для интерфейса — также внешний вид и взаимодействие. Для простой правки текста не нужны фиктивные тесты.
- При изменении запуска, данных, контрактов или решения обновить соответствующие документы. Не включать секреты, реальные данные учеников и абсолютные пути рабочей машины в публикуемые материалы.
- Неполный результат не считать готовым. Если оставшуюся работу блокирует вопрос или внешняя зависимость, сообщить точную причину и актуальный статус. Черновой PR допустим для порученной проверки незавершенной работы при разрешенной публикации.

## 5. Commit, push и PR

Повторно учесть ограничения поручения. Добавлять в индекс только проверенные файлы задачи и просматривать staged diff:

```bash
git add <проверенные-пути>
git diff --cached --stat
git diff --cached
git diff --cached --check
```

Создать логически цельный commit с префиксом по сути изменения: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:` или `ci:`. Затем явно отправить ветку:

```bash
git push --set-upstream origin "$BRANCH"
```

До создания PR проверить, нет ли PR этой ветки. Заполнить `.github/pull_request_template.md` во временном файле. Указать `Closes #<номер>`, конечный результат, фактическую приемку, проверки и существенные ограничения; удалить незаполненные подсказки. Добавить безопасные изображения измененного интерфейса, когда применимо.

Передать тело через `--body-file`, сохранив настоящие переводы строк. Не подставлять текст Issue в исполняемый shell-код. `PR_TITLE` описывает итоговый результат, `PR_BODY_FILE` указывает на существующий проверенный файл.

```bash
gh pr create --repo "$REPOSITORY" \
  --base "$DEFAULT_BRANCH" --head "$BRANCH" \
  --title "$PR_TITLE" --assignee "@me" --body-file "$PR_BODY_FILE"
```

Проверить созданный PR, его базу, ветку и проверки. При наличии CI дождаться обязательных проверок; при сбое исправить и повторить затронутые проверки. Отсутствие CI явно отметить, не считать его зеленым запуском.

Готовый PR перевести в `status: needs-review` на Issue. Сообщить ссылки на Issue и PR, результат, проверки и ограничения. В локальном режиме вместо PR указать подготовленные файлы и причину отсутствия публикации.

## 6. Замечания, слияние и уборка

- Исправлять замечания в той же ветке и PR, повторять затронутые проверки и обновлять описание по окончательному результату.
- Сливать конкретный PR только при явном поручении пользователя, включая уже данное. Успешный CI и положительный review сами по себе не разрешают merge.
- Перед merge повторно проверить PR: правильные репозиторий и база, ожидаемые изменения, открытое состояние без draft, успешные обязательные проверки, отсутствие конфликтов и блокирующих замечаний.
- Проверить актуальный head commit. Новые изменения за пределами разрешенного объема либо изменение явно одобренного commit требуют повторной оценки и уточнения разрешения. Не запрашивать его повторно без изменения условий.
- Если правила репозитория не задают стратегию и squash разрешен, использовать squash и `--match-head-commit` с проверенным SHA. Не обходить обязательные проверки административным merge.
- Проверить `MERGED` и закрытие Issue. Удалить устаревшую статусную метку с закрытой Issue.
- Удалять только связанные с завершенной задачей ветку и рабочее дерево после проверки отсутствия незакоммиченной или неопубликованной работы. Не удалять дерево текущей активной сессии: его уборку завершать из другого checkout.
- Предпочитать `git branch -d`. После squash принудительное удаление допустимо только при подтвержденном `MERGED` и совпадении локального tip с head слитого PR. Удаленную ветку не удалять, если она получила новые коммиты после merge.
- Основную ветку обновлять через `pull --ff-only` только в чистом checkout, где она уже выбрана. Не переключать пользовательскую ветку и не сбрасывать изменения ради уборки.

В отчете после завершения указать ссылку на слитый PR, состояние Issue и фактически выполненную уборку.
