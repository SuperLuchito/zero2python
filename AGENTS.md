# Работа над zero2python

## Проект

`zero2python` — учебная платформа для команды, которая осваивает Python, ML и компьютерное зрение с нуля. Три направления: Python с практикой, нейросети по книге «Грокаем глубокое обучение» и университетский анализ данных с доступом после необходимых тем Python.

Репозиторий: `SuperLuchito/zero2python`. Существующий каркас: Next.js App Router, React, TypeScript; Python выполняется в браузере через Pyodide. Развивать этот каркас, не заменять стек только потому, что предмет обучения — Python.

## Начало работы

1. Прочитать этот файл и локальные `AGENTS.md` затрагиваемых каталогов.
2. Для реализации GitHub Issue использовать [github-issue-flow](.agents/skills/github-issue-flow/SKILL.md). Для изменения кода и выбора зависимостей прочитать [ponytail](.agents/skills/ponytail/SKILL.md).
3. Проверить текущее состояние Git и прочитать задачу, [описание продукта](docs/product.md), относящиеся к изменению части [системы](docs/system.md) и [решения](docs/decisions/README.md).
4. Выполнить задачу в ее границах, проверить результат и обновить документацию, которую изменение затрагивает.

Первичная настройка по прямому поручению и локальная подготовка допустимы без Issue. Запрет пользователя на публикацию имеет приоритет над обычным Issue → PR процессом. Наличие файлов GitHub-шаблонов или `origin` само по себе не разрешает push.

## Навыки и реализация

- `github-issue-flow` отвечает за Issue, ветку, рабочее дерево, проверки, commit, push, PR и завершение задачи.
- `ponytail` помогает выбрать простое достаточное решение: сначала понять существующий код, затем использовать готовые возможности проекта, стандартной библиотеки и платформы.
- Исполнитель задачи сам реализует и проверяет изменения. Обязательной передачи другому инструменту или агенту нет.
- Ponytail не отменяет требования пользователя, читаемость учебных примеров, доступность интерфейса, обработку ошибок и проверку результата. Его рекомендации по краткости не ограничивают объяснения, необходимые новичкам.

## Вопросы и документы

- Общаться с командой и писать проектную документацию по-русски; имена файлов, API и идентификаторы оставлять в принятом в коде формате.
- Сначала искать ответ в коде, Issue и подтвержденных документах. Спрашивать только о существенном неизвестном, которое нельзя надежно установить самостоятельно.
- При вопросе кратко объяснять, какое решение он блокирует. Продолжать независимую работу; технические мелочи решать самостоятельно в рамках поручения.
- Не выдавать открытые вопросы за требования. В `docs/questions.md` хранить вопрос, его влияние, статус и ответ со ссылкой на решение или датой подтверждения.
- Обновлять основной документ после принятого ответа. Не дублировать все требования в нескольких местах и не переносить всю историю обсуждения в PR.
- Значимые решения оформлять ADR со статусом, контекстом, вариантами и последствиями. Замененное решение сохранять со ссылкой на новое. Для мелких обратимых правок ADR не нужен.
- Не создавать спецификации и пустые модули «на будущее» без текущей потребности.

## GitHub

- Одна Issue — одна ветка `issue/<номер>-<краткое-название>` и один связанный PR. Возобновлять существующую работу, а не создавать дубликаты.
- Прямое поручение выполнить готовую Issue разрешает обычные действия до PR включительно, если пользователь не ограничил их. Слияние выполнять только по явному поручению на конкретный PR; уже данное разрешение не запрашивать повторно без изменения его условий.
- Не делать прямой push в основную ветку в обычном потоке. Первичная публикация в пустой репозиторий — отдельное поручение.
- Не стирать чужие изменения, не применять автоматический stash, reset или force-push ради удобства.
- Шаблоны находятся в `.github/`, названия меток — в `.github/labels.yml`. Их наличие локально не означает, что они уже настроены на GitHub.

## Готовность результата

- Критерии задачи выполнены, diff соответствует ее границам.
- Запущены проверки, подходящие к изменению; результат указан честно. Команды брать из реального проекта, не придумывать отсутствующие сборку или CI.
- Для значимого изменения поведения проверять соответствующий сценарий; для интерфейса — также внешний вид и взаимодействие. Простые правки документации проверять на согласованность и рабочие ссылки.
- Если менялись запуск, контракт или решение, обновить соответствующий документ.
- При разрешенной публикации PR связан с Issue через `Closes #<номер>`; в локальном режиме отдать проверенные файлы и явно назвать то, что еще не опубликовано.

## Команды и области кода

- `npm ci` — установка по `package-lock.json`; `npm run dev` — локальная разработка; `npm run build` и `npm start` — сборка и запуск.
- `node node_modules/typescript/bin/tsc --noEmit --incremental false` — проверка типов. Отдельных команд lint/test и CI в каркасе пока нет; не объявлять их выполненными.
- `app/` содержит маршруты и глобальные стили, `components/` — интерфейс, `content/` — уроки и вопросы, `lib/` — типы, прогресс и Pyodide.
- При изменении типов или логики проверить TypeScript; при изменении сборки или маршрутов — сборку; при изменении интерфейса — затронутые пользовательские сценарии. Чистая правка документов требует проверки текста и ссылок.
- Не коммитить `.next/`, `node_modules/`, `out/` и локальные результаты проверок. Существующее имя пакета `python-terminal` менять только в рамках соответствующей задачи.

## Данные и учебный контент

- Не коммитить секреты, учетные записи учеников и их реальные результаты. Примеры и тестовые данные должны быть синтетическими.
- Книгу и материалы университета использовать после получения. Не приписывать источникам задания или содержание, которых в них не проверяли.
- Доступ к разделу анализа данных зависит от освоенных предпосылок. Конкретный порог и способ проверки пока открыты; не выбирать их молча при реализации.
- Python уже выполняется клиентским Pyodide. При изменении этого механизма определить границу исполнения и изоляцию; не переносить недоверенный код в серверный процесс основного приложения.
